# 需求文档撰写指南

## 1. 撰写前准备

### 1.1 参考模板
- 需求文档撰写需严格参考【需求文档模板.md】的要求
- 确保文档结构和内容与模板保持一致

### 1.2 准备工作
- 收集充分的业务需求信息
- 了解项目背景和目标
- 明确用户角色和使用场景
- 整理业务流程和数据流

## 2. 结构规范

### 2.1 文档结构
1. **变更记录**：记录需求的增删改及修改人、修改时间、修改内容
2. **文档概述**：文档目的、术语定义
3. **项目背景**：项目简介、业务痛点、项目目标
4. **业务场景**：典型业务场景、业务流程
5. **目标用户**：用户角色、用户需求
6. **产品结构**：系统整体架构、模块关系、技术实现建议
7. **流程图**：系统整体流程、核心业务流程
8. **高保真原型**：设计风格、页面设计、交互设计
9. **功能需求**：各功能模块的详细需求
   - 每个功能模块下包含：
     - 功能描述
     - 详细需求
     - 字段定义
     - 筛选字段（如有）
     - 操作逻辑
     - 状态流转
     - 数据权限
10. **非功能需求**：性能要求、可靠性要求、安全性要求、易用性要求
11. **项目范围**：包含范围、排除范围
12. **风险分析**：风险识别、风险缓解措施
13. **验收标准**：功能验收、性能验收、安全验收、可用性验收
14. **交付物**：文档交付物、代码交付物、其他交付物
15. **项目时间计划**：项目阶段、关键里程碑
16. **联系方式**：项目团队、沟通方式

### 2.2 模块详细信息放置
- 模块详细信息（字段定义、操作逻辑、状态流转、数据权限）应放置在对应功能需求子模块下
- 避免将所有模块详细信息集中在一个单独的章节

## 3. 格式规范

### 3.1 编码规范
- 使用UTF-8编码保存文档
- 避免使用特殊字符，确保文档在不同设备上正常显示

### 3.2 排版规范
- 使用Markdown格式撰写文档
- 标题层级清晰，使用#、##、###等标记
- 表格使用Markdown表格格式
- 代码块和流程图使用适当的Markdown语法

### 3.3 命名规范
- 文档命名：[项目名称]需求文档.md
- 文件名使用中文，清晰描述文档内容
- 避免使用特殊字符和空格

## 4. 内容规范

### 4.1 变更记录
- 每次修改都需记录在变更记录中
- 包含版本号、日期、变更内容、变更人
- 版本号使用语义化版本（如1.0、1.1、2.0等）

### 4.2 字段定义
- 列出所有相关字段的名称、类型、取值逻辑
- 使用表格形式展示，确保清晰易读
- 字段类型需明确（如字符串、数字、日期、枚举等）

### 4.3 操作逻辑
- 描述所有操作按钮的操作逻辑
- 包含成功提示和错误提示
- 使用表格形式展示，确保完整覆盖

### 4.4 状态流转
- 描述业务流程中的状态变化
- 使用流程图或文本形式展示状态流转
- 确保状态流转逻辑清晰合理

### 4.5 数据权限
- 描述不同角色的数据访问权限
- 明确权限限制和范围
- 使用表格形式展示，确保权限定义清晰

## 5. 审核与检查

### 5.1 撰写完成后审核
- 检查文档结构是否完整
- 检查所有必要信息是否填写
- 检查格式是否规范
- 检查内容是否一致和准确

### 5.2 定期检查
- 定期检查需求文档的完整性
- 确保需求文档与实际业务需求保持一致
- 及时更新需求文档以反映业务变化

### 5.3 质量检查
- 参考【作业规范.md】中的质量检查清单
- 确保文档符合质量要求
- 如有问题，及时修改和完善

## 6. 注意事项

### 6.1 版本管理
- 使用Git进行版本控制
- 定期提交需求文档的修改
- 避免直接在主分支上修改，使用功能分支

### 6.2 协作规范
- 多人协作时，明确分工和责任
- 建立需求变更审批流程
- 确保所有修改都有记录和审核

### 6.3 文档维护
- 需求文档应与项目进展保持同步
- 项目变更时，及时更新需求文档
- 保留历史版本，便于追溯变更

### 6.4 其他注意事项
- 避免使用模糊或歧义的描述
- 确保文档语言清晰、专业
- 关注细节，确保文档的准确性和完整性
- 参考过往项目的需求文档，学习最佳实践
